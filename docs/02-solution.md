# 02 方案

## 调用流程

```
问题 + 历史 ──► ReActAgent.run
                  │
            ┌──► 模型选择动作 + decision_note
            │     ├─ search_docs：返回 ID、版本日期、预览（预览不能作为引用）
            │     ├─ read_snippet：返回原文、版本日期、适用范围
            │     └─ finish ──► guard：核对引用是否原文、数字是否有出处 ──► 最终结果
            └── 未 finish 且未超限：下一轮；超限 ──► incomplete
```

## 动态决策点

| 观察 | 可选动作 |
|---|---|
| 问题是追问且有 history | 补全指代后检索（“那二线城市呢” → “住宿标准 二线城市”） |
| 问题是追问但没有 history | 不检索，`needs_clarification` |
| `search_docs.count = 0` | 改写成规范用语再检索；多次无果 → `out_of_scope` |
| 命中多条 | 读取相关片段原文，比较内容、版本日期、适用范围 |
| 两份文档对同一事项规定不同，且未说明优先级 | 列出冲突与各自引用，`conflict_needs_confirmation`，提出确认问题 |
| 只有一份相关文档 | 依据原文回答并引用 |
| 工具失败 | 重试一次；仍失败 → `failed`，不凭记忆回答 |

## 为什么检索器只给预览、而且故意不够聪明

- 预览只有前 16 个字。模型必须调用 `read_snippet` 读原文才能引用，“检索 → 读取”成为两个需要模型决策的动作。
- 检索用字符二元组重合度：“每年能歇多久”与“年假”没有重合，必定检索不到。这样“改写后的相似问题”能真正检验模型会不会改写查询，而不是被一个强检索器掩盖。

## 结束护栏

模型调用 `finish` 后，`guard` 只做能用事实判定的核对：

1. 每条引用必须对应本轮 `read_snippet` 读到的片段，quote 必须是原文子串，否则删除；
2. 答案中的每个数字必须出现在有效引用的原文、文档 ID 或版本日期中，否则撤回答案并改为 `insufficient_evidence`；
3. 标为 answered 却没有有效引用 → `insufficient_evidence`；检索全部失败却给出答案 → `failed`；
4. 冲突或澄清状态没有问题时补一个确认问题。

护栏**不**判断哪些文档冲突、不替模型选答案；这部分是模型的查证能力，由验收用例 c02/c03/c11 检查。

## 技术取舍

| 选择 | 理由 | 代价 |
|---|---|---|
| 原生循环，不用框架 | 步数上限、finish 校验、Trace 字段可精确控制 | 没有现成的检索组件 |
| 二元组检索而非向量检索 | 零依赖、可复现，且能暴露“需要改写查询”的场景 | 召回弱，规模大时不可用 |
| 引用要求逐字原文 | 可以机械校验，杜绝“看起来像引用”的转述 | 回答需要原文与解释分开写 |
| 数字出处核对 | 制度问答里最危险的错误是数字错（天数、金额），且最容易机械检查 | 不能检查非数字的事实错误 |
| 冲突交给模型判断、由用例检查 | 系统不应预先知道哪些文档冲突，否则就不是 Agent 在查证 | 真实模型漏判冲突时护栏拦不住，只能在评估中暴露 |
| OpenAI 兼容接口 + `decision_note` + `finish` 工具 | 同题 1 | 各家 function calling 细节不同 |
