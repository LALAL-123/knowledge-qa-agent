# 01 需求

## 用户

公司员工。问制度（报销、年假、差旅、加班）或产品（X1 相机）问题，需要可以拿去对照原文的答案。

## 目标

| 输出字段 | 含义 |
|---|---|
| `answer` | 回答；冲突、资料外、失败时说明情况 |
| `citations` | 文档 ID、片段 ID、逐字原文、版本日期、适用范围 |
| `conflicts` | 冲突涉及的文档与说明 |
| `gaps` | 资料缺口 |
| `clarifying_question` | 需要用户确认或补充的问题 |
| `task_status` | answered / conflict_needs_confirmation / needs_clarification / out_of_scope / failed / insufficient_evidence / incomplete |
| `evidence_check` | 有效引用数、无出处数字、读取片段数、检索次数 |

## 输入

```json
{"question": "那二线城市呢？",
 "history": [{"role": "user", "content": "出差住宿标准是多少？"},
             {"role": "assistant", "content": "一线城市……不超过 500 元（D05-S1）。"}]}
```

材料：`data/docs.json`，6 份合成文档（D01–D06），每份带版本日期、适用范围和若干片段。其中 D01“30 天”与 D02“15 天”对报销期限规定不同，且都未注明适用范围与优先级。

## 范围

做：检索、查询改写、原文读取、冲突识别与确认、上下文追问、资料外判定、工具失败处理、引用核对。

不做：向量检索、权限过滤、文档版本自动裁决、多轮会话存储、界面。

## 成功标准

1. 六个必须验收点（明确答案、文档冲突、资料外问题、改写后的相似问题、上下文追问、工具失败）各有用例且检查全部通过。
2. 关键缺陷为零：
   - 每条引用的 quote 都逐字出现在对应原文；
   - 答案中的数字都能在引用原文中找到；
   - 冲突时不擅自选一个答案（参考实例不能只答 15 天）；
   - 资料外或工具失败时不给出带事实的答案。
3. 替换文档内容后答案和动作随之改变（c03 删除 D02、c11 改写 D03）。
4. 达到步数或调用上限时返回 `incomplete`。
5. 至少两条执行路径体现动作随工具结果改变：首检命中直接读原文（c01）vs 首检无命中先改写再检索（c05）；读到两份冲突文档请求确认（c02）vs 只读到一份直接回答（c03）。
